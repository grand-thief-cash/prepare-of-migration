# iptables: Tables, Chains, Rules, and the Packet Processing Path

> The goal is not to memorize commands, but to build a correct mental model:
>
> **Table decides *what kind of processing* the rule belongs to;
> a Chain is a list of rules executed in order;
> a Rule decides *what packet matches* and *what happens when it does*.**
>
> The Linux kernel processes packets along an actual path:
>
> `PREROUTING → routing decision → INPUT / FORWARD → OUTPUT → POSTROUTING`
>
> The chains of different tables are executed in order at those positions.

---

## 1. The big picture

```
                         PACKET
                           │
                           ▼
                     PREROUTING
                           │
                           ▼
                    ┌── ROUTING ──┐
                    │             │
              local destination  elsewhere
                    │             │
                    ▼             ▼
                  INPUT        FORWARD
                    │             │
                    ▼             │
                application       │
                    │             │
                    ▼             ▼
                  OUTPUT ───────► POSTROUTING
                                    │
                                    ▼
                                 network
```

Two ways to read this picture:

- The **chain names** describe *where the packet is* in its journey.
- The **tables** describe *what you're trying to do* to that packet.

---

## 2. The three-layer structure

iptables can be abstracted as:

```
TABLE
  │
  └── CHAIN
        │
        ├── RULE
        ├── RULE
        └── RULE
```

Each layer answers a different question:

| Concept | Core question                                   | Example                            |
| ------- | ----------------------------------------------- | ---------------------------------- |
| Table   | What is this class of rules responsible for?    | `filter`, `nat`, `mangle`          |
| Chain   | Where in packet processing do these rules run?  | `INPUT`, `OUTPUT`, `FORWARD`       |
| Rule    | Which packets match? What happens when they do? | `-p tcp --dport 80 -j ACCEPT`      |

---

## 3. Tables: classification by function

```
iptables
│
├── filter
├── nat
├── mangle
├── raw
└── security
```

| Table    | Responsibility                        | Typical use                              |
| -------- | ------------------------------------- | ---------------------------------------- |
| filter   | Allow/block traffic                   | Firewall: `ACCEPT` / `DROP`              |
| nat      | Address/port translation              | `DNAT` / `SNAT` / `MASQUERADE`           |
| mangle   | Modify packet metadata                | Marks, QoS, TTL manipulation             |
| raw      | Special connection tracking control   | Usually advanced cases                   |
| security | Security-related processing           | SELinux etc., advanced                   |

When learning, master `filter` and `nat` first; `mangle`, `raw`, and `security` can come later.

A useful way to frame the two most common tables:

```
filter → "Can this packet pass?"

nat    → "Should this packet's address/port be translated?"
```

They are fundamentally different kinds of processing, which is why they live in different tables.

---

## 4. Chains: an ordered list of rules

A chain is simply a set of rules checked in order.

```
filter table
│
└── INPUT chain
      │
      ├── rule 1
      ├── rule 2
      ├── rule 3
      └── rule 4
```

Why is it called a *chain*? Because the rules link together — a packet flows down the link until it matches:

```
packet
  │
  ▼
rule 1 ── match? ── YES ──► target/action
  │
  NO
  ▼
rule 2 ── match? ── YES ──► target/action
  │
  NO
  ▼
rule 3 ...
```

### 4.1 Built-in chains

iptables has predefined chains, each corresponding to a specific position in the kernel's packet processing path. The most important:

`PREROUTING`, `INPUT`, `FORWARD`, `OUTPUT`, `POSTROUTING`

#### INPUT — packets coming into this machine

```
Internet ───────► Linux server
                       │
                     INPUT
                       │
                       ▼
                    nginx
```

If you want to block SSH access to this server, you're dealing with INPUT:

```
iptables -A INPUT -p tcp --dport 22 -j DROP
```

#### OUTPUT — packets generated by this machine

```
Linux server
     │
   OUTPUT
     │
     ▼
  Internet
```

For example, blocking this machine from making outbound HTTP connections:

```
iptables -A OUTPUT -p tcp --dport 80 -j DROP
```

#### FORWARD — packets passing through this machine

The machine is not the destination; it just forwards. Extremely important when Linux acts as a:

- router
- gateway
- firewall
- VPN router

```
LAN ───► Linux router ───► Internet
              │
           FORWARD
```

If the Linux machine itself isn't the destination, the packet generally goes through FORWARD.

#### PREROUTING — before the routing decision

The packet has just entered the system, but the kernel hasn't yet decided where it's going. Particularly important for NAT — destination NAT / port forwarding commonly happens here:

```
packet arrives
     │
     ▼
PREROUTING
     │
     ▼
routing decision
```

#### POSTROUTING — after the routing decision

Just before the packet leaves. Commonly used for source NAT:

```
routing
   │
   ▼
POSTROUTING
   │
   ▼
packet leaves
```

Classic Linux router/NAT rule:

```
iptables -t nat -A POSTROUTING -o eth0 -j MASQUERADE
```

### 4.2 Custom chains

Users can also create their own chains:

```
iptables -N SSH_RULES
```

Important: this does **not** create a new packet-processing stage. It only creates a group of rules you manage yourself:

```
SSH_RULES
│
├── rule 1
├── rule 2
└── rule 3
```

Then an existing chain can jump to it:

```
iptables -A INPUT -p tcp --dport 22 -j SSH_RULES
```

So `SSH_RULES` and `INPUT` are two *independent* chains in the same table — not a nested structure:

```
filter table
│
├── INPUT
├── OUTPUT
├── FORWARD
└── SSH_RULES      ← sibling of INPUT, not a child
```

Only a jump rule creates a logical relationship:

```
filter.INPUT
      │
      │ jump
      ▼
filter.SSH_RULES
      │
      ├── rule 1
      ├── rule 2
      └── rule 3
```

This is also why custom chains are not part of the packet path: they are never executed on their own — a packet only reaches them if some rule jumps to them.

## 5. Rules: match + target

Example:

```
iptables -A INPUT -p tcp --dport 80 -j ACCEPT
```

Broken down:

```
iptables
   │
   ├── -A INPUT
   │      ↓
   │   append to the INPUT chain
   │
   ├── -p tcp
   │      ↓
   │   protocol = TCP
   │
   ├── --dport 80
   │      ↓
   │   destination port = 80
   │
   └── -j ACCEPT
          ↓
       action/target = ACCEPT
```

Abstracted:

```
RULE
│
├── MATCH
│     ├── protocol = tcp
│     └── destination port = 80
│
└── TARGET
      └── ACCEPT
```

So: **Rule = matching conditions + target/action**.

### 5.1 Rule order matters

Rules are checked in the order they appear in the chain:

```
iptables -A INPUT -p tcp --dport 22 -j ACCEPT
iptables -A INPUT -p tcp --dport 22 -j DROP
```

For TCP port 22, the first rule matches, `ACCEPT` is a *terminating verdict*, and the `DROP` is never reached:

```
packet
  │
  ▼
rule 1 ── match? ── YES ──► ACCEPT
  │
  NO
  ▼
rule 2 ── match? ── YES ──► DROP
  │
  NO
  ▼
rule 3
```

This is why "allow first, then deny" and "deny first, then allow" can produce completely different results.

## 6. The true relationship between tables and chains

The structure is:

```
TABLE
  │
  ├── CHAIN
  │     ├── RULE
  │     ├── RULE
  │     └── RULE
  │
  ├── CHAIN
  │     ├── RULE
  │     └── RULE
  │
  └── CHAIN
        ├── RULE
        └── RULE
```

Concretely:

```
filter table          nat table            mangle table
│                     │                    │
├── INPUT              ├── PREROUTING       ├── PREROUTING
├── OUTPUT             ├── INPUT            ├── INPUT
└── FORWARD            ├── OUTPUT           ├── FORWARD
                       ├── FORWARD          ├── OUTPUT
                       └── POSTROUTING      └── POSTROUTING
```

(Note: not every table has every chain — e.g. `filter` has no `PREROUTING`/`POSTROUTING`.)

### 6.1 A very easy misunderstanding: same-named chains

Different tables can have chains with the same name:

```
filter table ─── INPUT
nat table    ─── INPUT
mangle table ─── INPUT
```

These three `INPUT`s are **not the same chain**. It helps to write them as:

```
filter.INPUT
nat.INPUT
mangle.INPUT
```

Similarly, `mangle.PREROUTING` and `nat.PREROUTING` are two different chains that merely share a name.

### 6.2 Why you usually don't see the table in commands

```
iptables -A INPUT -p tcp --dport 80 -j ACCEPT
```

There's no `-t filter` here, but the filter table is implied. This command is exactly equivalent to:

```
iptables -t filter -A INPUT -p tcp --dport 80 -j ACCEPT
```

So it's not that "iptables only needs chains, not tables" — `filter` is simply the *default table*, so simple firewall commands omit `-t`.

What does `-t` do? It selects which table to operate on:

```
iptables -t nat -A POSTROUTING -o eth0 -j MASQUERADE
```

means:

```
nat table
    ↓
POSTROUTING chain
    ↓
MASQUERADE rule
```

## 7. The packet processing path in detail

Now connect tables, chains, and rules to the real packet flow.

### 7.1 One position executes several tables' chains in order

At the PREROUTING position (packet just arrived, routing not yet decided), the kernel walks the corresponding chains of several tables:

```
packet
  │
  ▼
raw.PREROUTING
  │
  ▼
mangle.PREROUTING
  │
  ▼
nat.PREROUTING
  │
  ▼
routing decision
```

Strictly speaking, one should **not** say "a PREROUTING chain belongs to two tables". The correct statement is:

> The mangle table has a PREROUTING chain, and the nat table also has a PREROUTING chain; they are executed in order at the PREROUTING position of the packet path.

The same applies to INPUT. For a packet whose destination is this machine:

```
packet
  │
  ▼
PREROUTING
  │
  ▼
routing decision
  │
  ▼
INPUT position:  mangle.INPUT → filter.INPUT
  │
  ▼
local application
```

Again: `mangle.INPUT` and `filter.INPUT` are two different chains that both correspond to the INPUT position of the packet path.

### 7.2 The full map with table order per position

```
                    ┌─────────────────────┐
                    │       PACKET        │
                    └──────────┬──────────┘
                               │
                               ▼
                    ┌──────────────────────┐
                    │   PREROUTING stage   │
                    │                      │
                    │ raw.PREROUTING       │
                    │        ↓             │
                    │ mangle.PREROUTING    │
                    │        ↓             │
                    │ nat.PREROUTING       │
                    └──────────┬───────────┘
                               │
                               ▼
                         ROUTING DECISION
                           /           \
                          /             \
                         ▼               ▼
              ┌────────────────┐   ┌─────────────────┐
              │ INPUT position │   │FORWARD position │
              │                │   │                 │
              │ mangle.INPUT   │   │mangle.FORWARD   │
              │      ↓         │   │      ↓          │
              │ filter.INPUT   │   │filter.FORWARD   │
              └───────┬────────┘   └────────┬────────┘
                      │                     │
                      ▼                     │
                LOCAL PROCESS               │
                      │                     │
                      ▼                     │
              ┌──────────────┐              │
              │OUTPUT stage  │              │
              │              │              │
              │raw.OUTPUT    │              │
              │     ↓        │              │
              │mangle.OUTPUT │              │
              │     ↓        │              │
              │nat.OUTPUT    │              │
              │     ↓        │              │
              │filter.OUTPUT │              │
              └──────┬───────┘              │
                      │                     │
                      └──────────┬──────────┘
                                 │
                                 ▼
                    ┌──────────────────────┐
                    │   POSTROUTING stage  │
                    │                      │
                    │ mangle.POSTROUTING   │
                    │        ↓             │
                    │ nat.POSTROUTING      │
                    └──────────┬───────────┘
                               │
                               ▼
                            NETWORK
```

## 8. The dual perspective

The best way to understand iptables is to hold two views at once.

**Perspective A — the data structure** (what `iptables -L` shows):

```
TABLE
│
├── CHAIN
│    │
│    ├── RULE
│    ├── RULE
│    └── RULE
│
└── CHAIN
     │
     ├── RULE
     └── RULE
```

**Perspective B — the packet processing path** (what actually happens):

```
packet
  │
  ▼
PREROUTING
  │
  ▼
routing
  │
  ├───────────────┐
  ▼               ▼
INPUT           FORWARD
  │               │
  ▼               │
process           │
  │               │
  └───────┬───────┘
          ▼
      POSTROUTING
```

And the subtle point connecting them: `PREROUTING`, `INPUT`, `FORWARD`, `OUTPUT`, `POSTROUTING` are **both**:

- *packet-path positions* — stages the kernel walks a packet through; and
- *iptables objects* — the names of built-in chains inside each table.

The two concepts are related but not identical. Same name, two readings:

- `INPUT` as a packet path position: "the packet is about to be handed to local processing"
- `INPUT` as an iptables object: "a chain named INPUT in some table"

## 9. A worked example: DNAT port forwarding

Setup: users access `Linux_Public_IP:8080` and it should be forwarded to `192.168.1.100:80`.

```
Internet
    │
    │ TCP :8080
    ▼
Linux router
    │
    ▼
192.168.1.100:80
```

The two rules:

```
iptables -t nat    -A PREROUTING  -p tcp --dport 8080 -j DNAT --to-destination 192.168.1.100:80
iptables -t filter -A FORWARD     -p tcp -d 192.168.1.100 --dport 80 -j ACCEPT
```

And the packet's journey:

```
packet arrives
   │
   ▼
raw.PREROUTING
   │
   ▼
mangle.PREROUTING
   │
   ▼
nat.PREROUTING
   │
   │ DNAT: 8080 → 192.168.1.100:80     ← address rewritten BEFORE routing
   ▼
routing decision                      ← now routed to 192.168.1.100 → forward
   │
   ▼
mangle.FORWARD
   │
   ▼
filter.FORWARD
   │
   │ ACCEPT
   │
   ▼
mangle.POSTROUTING
   │
   ▼
nat.POSTROUTING
   │
   ▼
192.168.1.100
```

Two things worth noticing:

1. DNAT happens in **PREROUTING**, *before* the routing decision — that's precisely why the DNAT table position matters: rewriting the destination *before* routing lets the kernel route the packet to the new address.
2. `mangle`, `nat`, `filter` here are not three "packet processing stages" — they are three different **tables**. The actual stages are `PREROUTING`, `FORWARD`, `POSTROUTING`, and each table may own a chain at each stage.

### 9.1 filter vs nat on the same port

The same target port can appear in both tables doing completely different jobs:

```
filter.INPUT
    │
    └── TCP port 80 → ACCEPT          ← "may this packet reach me?"

nat.PREROUTING
    │
    └── TCP port 8080 → DNAT → 192.168.1.100:80    ← "where should this packet really go?"
```

## 10. A helpful analogy: the airport

- **Table** = the type of check
  - `filter` → allowed through or not?
  - `nat` → change the traveler's destination/address?
  - `mangle` → stamp/modify the traveler's documents?
- **Chain** = the checkpoint window (`PREROUTING`, `INPUT`, `FORWARD`, `OUTPUT`, `POSTROUTING`)
- **Rule** = the concrete check rule (e.g. "if passport = TCP and destination port = 80, then ACCEPT")

So:

```
Table → decides the type of processing
Chain → decides at which processing position a set of rules runs
Rule  → decides what matches and what happens
```

## 11. The key decision questions

Don't memorize hundreds of rules. When writing any rule, ask two questions.

**Question 1: Which table?** — "What am I trying to accomplish?"

```
Allow/block traffic?       → filter
Change addresses/ports?    → nat
Modify packet metadata?    → mangle
Special conntrack behavior → raw
```

**Question 2: Which chain?** — "Where is the packet going?"

```
Coming INTO this machine?  → INPUT
Generated BY this machine? → OUTPUT
Passing THROUGH it?        → FORWARD

Before routing?            → PREROUTING
After routing?             → POSTROUTING
```

That gets you surprisingly far.

## 12. Decomposing any iptables command

Given any command, read it in four steps. Example:

```
iptables -t filter -A INPUT -p tcp --dport 80 -j ACCEPT
```

① TABLE:

```
-t filter
    ↓
I'm operating on the filter table
```

② CHAIN:

```
-A INPUT
    ↓
append the rule to filter.INPUT
```

③ MATCH:

```
-p tcp
--dport 80
    ↓
match TCP destination port 80
```

④ TARGET:

```
-j ACCEPT
    ↓
if matched → ACCEPT
```

Result:

```
filter table
    │
    └── INPUT chain
          │
          └── TCP dport 80 → ACCEPT
```

And a nat example:

```
iptables -t nat -A POSTROUTING -o eth0 -j MASQUERADE
```

```
① TABLE:  nat
② CHAIN:  POSTROUTING
③ MATCH:  -o eth0        (outgoing via eth0)
④ TARGET: MASQUERADE     (rewrite source address)
```

Here the target is not `ACCEPT`/`DROP` but address translation — which is exactly why it needs the nat table.

## 13. One-sentence memory

If you only remember a few lines:

```
Table = type of processing
Chain = an ordered list of rules
Rule  = Match + Target/Action
```

And:

```
Table → Chain → Rule
```

The packet path:

```
PREROUTING → Routing → INPUT / FORWARD → OUTPUT → POSTROUTING
```

More precisely, `PREROUTING` / `INPUT` / `FORWARD` / `OUTPUT` / `POSTROUTING` are *both* the names of built-in chains and the names of positions in the packet processing path. So when you see:

```
mangle.PREROUTING
nat.PREROUTING
```

read it as: *the mangle table's PREROUTING chain and the nat table's PREROUTING chain are executed in order at the PREROUTING position of the packet path* — not "one PREROUTING chain shared by two tables".

The final mental model:

```
                 WHAT KIND OF PROCESSING?
                           │
                         TABLE
                           │
              ┌────────────┼────────────┐
              ▼            ▼            ▼
           filter         nat         mangle
              │            │            │
              └────────────┼────────────┘
                           │
                           ▼
                 WHERE IN PACKET PATH?
                           │
                         CHAIN
                           │
              ┌────────────┼────────────┐
              ▼            ▼            ▼
          PREROUTING      INPUT      FORWARD
              │
              ▼
                     WHAT EXACTLY?
                           │
                         RULE
                           │
                  ┌────────┴────────┐
                  ▼                 ▼
                MATCH             TARGET
             what packet?       what to do?
```

Core takeaway:

> **Table is the classification, Chain is the rule list, Rule is the concrete rule; built-in chains additionally correspond to specific positions in the Linux kernel's packet processing path.**
